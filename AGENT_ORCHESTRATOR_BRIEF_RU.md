# Памятка-ТЗ: экономная многомодельная разработка

> Историческая памятка v0.1. Уточнения пользователя после обсуждения: ядро включает
> Claude Code, Codex и OpenCode; бесплатные модели и OpenRouter отложены; единственный
> платный API первой версии — DeepSeek. После явного разрешения DeepSeek работает
> без повторных подтверждений и сложных денежных ограничений. Актуальные рамки
> реализации и проверенные ограничения ведутся в `docs/ARCHITECTURE.md` и `docs/STATE.md`.

**Версия:** 0.1 · **Дата:** 15 октября 2026 года  
**Назначение:** передать в Codex или другой harness как основу для поэтапной разработки. Конкретные библиотеки, схемы данных и команды установки уточняются в ходе реализации.

## 1. К чему пришли

Создаём систему, которая **с первого запроса распределяет работу между подходящими моделями и источниками доступа**, а при исчерпании одного из лимитов возобновляет работу через доступный резерв.

Цель — не максимально долго использовать самую дорогую модель и не любой ценой расходовать бесплатные квоты. Цель — **больше законченных и принятых задач при контролируемых расходах, без зависимости от одного недельного лимита**.

Исходная ситуация, со слов пользователя: Claude Max 20× при текущей нагрузке заканчивается примерно за день. Уже работает собственный skill: Claude Code декомпозирует задачу, пишет ТЗ и запускает Codex как исполнителя. Codex использует доступ через ChatGPT и уже снимает часть нагрузки. **Эту интеграцию сохраняем и развиваем, а не начинаем вместо неё другой проект.**

Решение сначала проверяется на личной работе пользователя, затем передаётся разработчикам команды с их собственными подключениями и лимитами.

## 2. Что именно разрабатываем

**Отдельный Python-проект в Git: локальный контроллер задач + адаптеры исполнителей + конфигурация маршрутов + skill для Claude Code.** Репозиторий может быть закрытым; публикация в открытый доступ не требуется.

Для пользователя это устанавливаемое дополнение к привычному процессу. Внутри — не только текстовый `SKILL.md`, но и исполняемый код, состояние задач, журнал событий, тесты и инструкция установки. Skills Claude Code позволяют поставлять инструкции и вспомогательные файлы/скрипты.[^1]

**Важное исправление прежнего обещания:** один skill не гарантирует продолжение после исчерпания Max. Если управляющая модель уже не может ответить, нельзя рассчитывать, что она сама выберет резерв и запустит его. Переключение должен уметь выполнить внешний процесс, а для дальнейших интеллектуальных решений нужна доступная резервная модель.

Поэтому разделяем:

- **Руководителя — роль модели:** понять задачу, составить план, распределить работу, принять результат.
- **Контроллер — обычный код:** запустить исполнителей, проверить ограничения, сохранить состояние, обработать сбой и выбрать разрешённый резерв.

Рабочая сессия должна запускаться под контроллером либо заранее подключаться к нему поддерживаемым способом. Простое копирование `SKILL.md` не создаёт внешний механизм восстановления. Точный способ работы с интерактивным интерфейсом проверяется прототипом; первая версия может использовать собственную команду запуска.

Остаток в 1% не делает подписку бесконечной. Проверяемый результат проекта — возможность запустить резервный режим **даже при нулевом остатке Max**, без предварительного ответа Claude.

## 3. Кто участвует и за что отвечает

| Компонент | Место в нашей системе |
|---|---|
| **Claude Code** | Основной пользовательский harness и исходный руководитель. Сильные модели — для сложного планирования и ответственных проверок; более экономные — для подходящих этапов. |
| **Codex** | Уже работающий исполнитель. Оставляем доступ через ChatGPT; выбираем доступную модель и уровень рассуждения по задаче. Предусматриваем возможность назначить его резервным руководителем. |
| **OpenCode** | Дополнительный harness-исполнитель, запускаемый по аналогии с Codex. Для разных задач использует разные разрешённые подключения. |
| **Сервис моделей OpenCode — Console/Zen** | Отдельный источник доступа, в том числе к действующим бесплатным предложениям. Сам harness и предоставляемая ему модель — разные части. |
| **OpenRouter** | API-шлюз и каталог моделей. Используем подходящие бесплатные маршруты; платные — только при явном разрешении и в пределах бюджета. |
| **DeepSeek API** | Прямой платный источник для подходящих задач и резервного режима. Возможность работы через него проверяем в выбранном harness. |
| **Anthropic API / OpenAI API** | Дополнительные платные резервы, когда оправданы качеством и разрешены бюджетом. Для собственной интеграции с OpenAI используем Responses API. |

Подписочный вход Codex и API-ключ — разные режимы доступа и оплаты. У Codex есть неинтерактивный запуск `codex exec` и структурированный вывод; у OpenCode — `opencode run` с выбором модели и JSON-событиями.[^3][^4][^5]

**DeepSeek Harness, Copilot и остальные инструменты — возможные последующие адаптеры, не обязательная часть первой версии.** Не подключаем всё только ради числа поддерживаемых сервисов.

## 4. Из каких блоков состоит проект

| Блок | Что должен делать |
|---|---|
| **Интеграция с Claude Code** | Skill объясняет, когда делегировать работу и как пользоваться контроллером. Hooks подключаются там, где нужны поддерживаемые автоматические события. |
| **Контроллер и маршрутизатор** | Ведут очередь и этапы задач, применяют правила выбора, ограничения расходов, повторов и параллельности. |
| **Адаптеры harness’ов** | Приводят запуск Claude Code, Codex и OpenCode к общему контракту: задание → события → результат либо понятная ошибка. |
| **Реестр подключений и моделей** | Хранит возможности, источник доступа, тариф, доступность, лимиты и результаты проверки пригодности. |
| **Состояние и восстановление** | Сохраняет план, решения, изменения, статусы исполнителей, результаты тестов и следующий шаг вне истории одной модели. |
| **Контроль качества и отчётность** | Проверяет результат, организует необходимое ревью, показывает фактические расходы и причины выбора маршрутов. |

Каждое назначение фиксирует отдельно: **роль → harness → модель → уровень рассуждения → провайдер/аккаунт → источник оплаты**. Название «Opus» или «Codex» само по себе недостаточно для понимания, что запущено и какой лимит расходуется.

Модель может предлагать маршрут, но запреты, доступные источники и денежные ограничения проверяет код. Обязательная задача контроллера — не позволить текстовой инструкции обойти эти ограничения.

## 5. Как распределяем работу с самого начала

Ниже — начальные гипотезы для проверки на реальных задачах, а не вечное правило «эта модель всегда лучше».

| Тип работы | Стартовая стратегия |
|---|---|
| Архитектура, неоднозначная постановка, сложное исследование | Сильная доступная модель-руководитель, достаточный уровень рассуждения. |
| Реализация по чёткому ТЗ | Codex либо более экономная модель в Claude Code — по результатам пилота. |
| Ограниченные правки, шаблонная работа, несложные тесты | Проверенная экономная/бесплатная модель через OpenCode или другой совместимый исполнитель. |
| Сложная диагностика, провал предыдущей попытки | Более сильный исполнитель или независимая вторая модель. |
| Критическое, в том числе adversarial review | Сильная проверяющая модель; по возможности отдельно от автора решения. |
| Форматирование, поиск по точному шаблону, запуск тестов | Обычные инструменты без дополнительного обращения к модели, когда этого достаточно. |

**Бесплатные предложения и Codex используем уже при полном Max**, если они подходят задаче. Сильную Claude бережём для этапов, где её применение действительно оправдано. Повышение класса исполнителя при неудаче — часть системы, а не исключение.

У Claude Code уже есть настройка `opusplan`: Opus для планирования и Sonnet для исполнения. Для отдельных подагентов можно задавать модель, не оставляя всё на наследовании. Эти возможности нужно проверить и переиспользовать, прежде чем писать собственную замену.[^2]

Названия моделей и поддерживаемые уровни рассуждения храним в конфигурации. Не предполагаем, что одинаковое слово `low` или `high` имеет одинаковый смысл и доступно у всех.

Первая версия переключает маршруты **на границах задач и этапов**, а не пытается незаметно менять модель посреди любого вызова инструмента. Не заставляем дорогого руководителя перечитывать полный журнал ради каждого мелкого действия.

**Экономная модель не гарантированно лучше сильной на простой задаче.** Проверяем гипотезу по качеству результата, количеству переделок и общей стоимости доведения задачи до приёмки.

## 6. Что происходит, когда Max закончился

Это обязательный сценарий проекта, а не дополнительное улучшение.

**Обнаружение.** Контроллер различает исчерпание квоты, временный предел скорости, сетевой сбой, ошибку авторизации и отсутствие денег. Для них нужны разные реакции; бесконечно повторять один запрос нельзя.

**Фиксация.** Контроллер использует последнее сохранённое состояние: что принято, что изменено, какие исполнители ещё работают и что осталось. Не рассчитывает получить финальную сводку от уже недоступной модели.

**Выбор резерва.** Согласно конфигурации запускает доступного руководителя: например, Claude Code с DeepSeek API, Codex с оставшейся подписочной квотой или разрешённую API-модель. Переход на платный источник возможен только при заранее выданном разрешении и доступном бюджете.

Смена оплаты «Claude по подписке → та же Claude через API» и смена модели «Claude → DeepSeek» — разные решения. Во втором случае нужно заново проверить пригодность руководителя; одинаковое качество не предполагается автоматически.

**Продолжение.** Новый руководитель получает пакет передачи задачи и тот же интерфейс к исполнителям. Codex, OpenCode и бесплатные источники не исчезают из процесса из-за замены руководителя. Уже запущенные задачи сначала сверяются по статусу, а не запускаются повторно вслепую.

Подключение DeepSeek API к Claude Code описано самой DeepSeek. Это подтверждает существование такого режима, но совместимость конкретных skills, инструментов и восстановления сессий должна быть проверена отдельно.[^11]

**Гарантируемая цель — управляемое возобновление без ожидания недельного сброса, а не отсутствие любой паузы.** Перезапуск процесса или перенос задачи в новую сессию допустим. Когда все разрешённые источники недоступны либо бюджет исчерпан, система сохраняет состояние и явно сообщает о причине остановки.

## 7. Бесплатные источники: что фиксируем точно

### OpenRouter

По опубликованным условиям на 15 октября 2026 года: **50 бесплатных запросов в день**, либо **1 000 в день после покупки не менее $10 кредитов**; ограничение скорости — **20 запросов в минуту**.[^7][^8]

Это увеличение дневной квоты в 20 раз, **не подписка за $10 в месяц** и не увеличение скорости в 20 раз. Квота общая для бесплатных моделей аккаунта, а не отдельная на каждую. Неудачные попытки тоже могут её расходовать. При пополнении нужно учитывать комиссию покупки кредитов.[^7][^8]

Это **запросы, не токены и не законченные задачи**: одна агентная задача может вызвать модель многократно. OpenRouter не превращает платную Claude в бесплатную. Пример с бесплатным Opus рассматриваем только как гипотетическую акцию, наличие которой требуется подтвердить.

Не выбираем OpenRouter из предположения, что тот же Anthropic API обязательно дешевле. Его роль в проекте — общий доступ, каталог и варианты маршрутизации; экономику конкретных платных маршрутов сравниваем отдельно.[^8]

### OpenCode

Сейчас в официальной документации присутствует **DeepSeek V4.1 Flash Free**, причём бесплатность заявлена на ограниченное время. Это предложение сервиса моделей OpenCode; к нему нельзя автоматически применять лимиты OpenRouter. Ранее прозвучавшее «DeepSeek Vision Flash» не используем как идентификатор модели.[^6]

### Как используем меняющийся каталог

Обновляем каталог при запуске и периодически, а также после ошибки исчезнувшей модели. Через Models API OpenRouter можно получать идентификаторы, цены и характеристики моделей.[^9]

Найденная бесплатная модель сначала становится **кандидатом**, затем проходит проверку необходимых инструментов, контекста, качества и правил обработки данных. Только после этого разрешается для соответствующих задач. Перед использованием проверяем актуальную цену и доступность; платная замена бесплатного маршрута без разрешения запрещена.

Готовый `openrouter/free` выбирает среди бесплатных моделей случайным образом с фильтрацией возможностей. Для воспроизводимых рабочих задач проекту нужен собственный список разрешённых вариантов, а не слепая передача всего в случайный маршрутизатор.[^10]

## 8. Обязательные ограничения и подводные камни

**Контекст.** Передаём исполнителю цель, границы работы, нужные файлы, критерии приёмки и существенные решения. Руководителю возвращаем краткий результат, ссылки на изменения и проверки, а не весь внутренний диалог. Резервному руководителю передаём более полный пакет состояния. Сводки не должны заменять доступ к самим файлам и проверяемым результатам.

**Параллельная работа.** Для изменений используем изолированные рабочие копии/ветки либо явно разделённые области. Один ответственный шаг объединяет изменения. Ограничиваем число агентов и глубину делегирования; запрещаем циклы «Claude запускает Codex, который бесконечно запускает Claude».

**Безопасное восстановление.** После неопределённого исхода сначала проверяем, что реально выполнено. Деплой, миграции, удаление и внешние отправки нельзя автоматически повторять как обычное чтение файла. Переход между моделями не должен расширять права доступа.

**Качество и цена.** Учитываем постановку задачи, проверку, повторные попытки и повторную передачу контекста. Для маленькой задачи оркестрация может оказаться дороже непосредственного выполнения — должен существовать прямой маршрут. Ограничиваем число попыток до усиления исполнителя или остановки.

**Прозрачность.** Показываем фактические harness, модель, источник оплаты и причину переключения. Где доступен официальный учёт — используем его; где нет — честно маркируем оценку либо неизвестный остаток. Не переводим условный процент Max в точное число API-токенов без доказанного соответствия.

**Данные и доступы.** Ключи и токены не попадают в Git, промпты и общие логи; каждому процессу доступны только нужные подключения. Маршруты ограничиваются политикой проекта: конфиденциальный код нельзя отдавать любому бесплатному провайдеру. Коллеги используют собственные аккаунты. Подписочные входы оставляем штатным клиентам; не строим общий сервер на сборе OAuth-токенов Max. Anthropic прямо ограничивает такое посредническое использование подписочных credentials.[^12]

## 9. План реализации

| Этап | Что делаем и какой результат получаем |
|---|---|
| **0. Разобрать рабочую основу** | Изучить существующий skill Claude Code → Codex, способы запуска, версии, модели, доступные подключения и типовые задачи. Зафиксировать текущие результаты как базу сравнения. |
| **1. Проверить продолжение без Max** | Через Codex создать небольшой прототип внешнего запуска и состояния. Выполнить одну реальную задачу на разрешённом резерве при отключённом Max. Сначала доказать этот сценарий, не разрабатывать весь продукт. |
| **2. Собрать общее ядро** | Python-пакет, конфигурация, контракт задания/результата, журнал, сохранение состояния. Существующий вызов Codex оформить адаптером; добавить Claude Code и OpenCode. Проверить фактические модели и источники оплаты. |
| **3. Ввести превентивное распределение** | Небольшая матрица типов задач, выбор роли/модели/уровня рассуждения, делегирование из skill, ограниченные повторы и усиление исполнителя. Сначала понятные правила, без самообучающегося сложного роутера. |
| **4. Автоматизировать восстановление** | Сценарии «Max уже пуст при запуске», «лимит закончился в процессе», «упал исполнитель», «есть незавершённое действие». Продолжение от сохранённого состояния, без потери и дублирования работы. |
| **5. Подключить динамические бесплатные источники** | Сначала проверенные маршруты OpenCode и OpenRouter, затем обновление каталога, проверка новых кандидатов, учёт квот и исключение недоступных. |
| **6. Провести пилот на своей работе** | Сравнить с исходным процессом качество, время, расход Max/Codex, API-затраты, число переделок и накладные расходы руководителя. Настроить правила по измерениям. |
| **7. Упаковать для команды** | Установка, обновление и удаление; шаблон конфигурации; проверка доступов; инструкции; тестовый проект. Проверить установку у коллеги без пользовательских ключей и ручного редактирования исходников. |

Разработку начинаем **в Codex с оставшимися лимитами**. Код, конфигурация и skill могут быть написаны там; пригодность для Claude Code подтверждается отдельными интеграционными тестами. Сам выбор инструмента разработки не освобождает от этой проверки.

## 10. Критерии готовности первой полезной версии

Первая версия считается полезной, когда одновременно выполнены три группы условий.

**Рабочий процесс:** существующий Claude Code → Codex не сломан; хотя бы один дополнительный маршрут OpenCode выполняет ограниченную задачу; подходящая работа уходит на экономный источник даже при доступном Max.

**Надёжность и контроль:** протестированы нулевой Max при старте и исчерпание в процессе; состояние сохраняется; нет повторного опасного действия; платные переходы ограничены явным бюджетом; пользователь видит, что использовано и почему.

**Измеримый эффект и переносимость:** есть сравнение законченных задач с исходным процессом без ухудшения согласованного качества; коллега может установить решение и подключить свои источники. Процент экономии заранее не обещается — его определяет пилот.

## 11. Что оставляем за рамками первой версии

Не строим новый Claude Code/Codex, универсальный преобразователь всех API, маркетплейс, сложную веб-панель и сотню интеграций. Готовые компоненты переиспользуем после проверки, но не подменяем этим тестирование всей цепочки.

Конкретные модели, численные бюджеты, поддерживаемые ОС, способ изоляции процессов и формат интерфейса уточняются при разработке. Три требования неизменны: **сохранить рабочий Codex, экономить до исчерпания лимитов и продолжать работу через резерв без зависимости от ответа недоступной модели**.

## Первое задание для Codex

> Изучи это ТЗ и существующую интеграцию Claude Code → Codex. Не переписывай рабочую часть без необходимости. Сначала предложи минимальный состав локального контроллера и проверь главный сценарий: разрешённый резерв запускается и выполняет ограниченную задачу при полностью недоступном Max. Покажи фактические harness, модель и источник оплаты, сохранённый результат и ограничения прототипа. После этого переходи к общей архитектуре и превентивной маршрутизации. Не реализуй все интеграции сразу; неизвестные параметры выделяй явно и уточняй по ходу соответствующего этапа.
