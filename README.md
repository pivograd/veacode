# Veacode

Локальный контроллер, который передаёт задачи Claude Code, Codex и OpenCode,
сохраняет ход работы и позволяет продолжить её через доступный маршрут.
Claude обычно планирует и проверяет, Codex реализует, OpenCode подключает DeepSeek API.
Порядок можно менять в конфигурации.

Сейчас это первая версия для личного пилота. Восстановление и переключение проверяются
локальными тестами с подставными исполнителями. Работоспособность всей связки с реальными
аккаунтами нужно отдельно подтвердить живым прогоном; результаты фиксируются в
[состоянии проекта](docs/STATE.md).

## Подключение GitHub на Windows

Из обычного PowerShell, где доступны штатные настройки Git и вход GitHub:

```powershell
& 'C:\Users\user\PycharmProjects\veacode\scripts\connect-github.ps1'
```

Скрипт проверит тесты, предложит войти в GitHub как `pivograd`, создаст приватный
`pivograd/veacode`, сохранит коммит и отправит `main`. Ключ DeepSeek и локальная
конфигурация исключены из Git. Если `origin` указывает на другой репозиторий или
истории расходятся, скрипт остановится. Силовой push и изменения ACL не выполняются.

## Установка

Нужны Python 3.12+, Git и [uv](https://docs.astral.sh/uv/getting-started/installation/).
Для выполнения задач нужны установленные CLI выбранных исполнителей и их обычный вход
в аккаунт. Claude и Codex используют подписки через собственные клиенты.

Из каталога Veacode:

```powershell
uv --cache-dir .venv/uv-cache sync
uv run veacode init
uv run veacode doctor
uv run veacode routes
```

`init` создаёт `veacode.toml`. Если файл уже существует, он сохранится.
`doctor` проверяет наличие CLI и доступный локальный статус входа без запросов к модели.
Остатки подписочных квот он не определяет.

Перед первым запуском проверь модели и порядок маршрутов в `veacode.toml`.
Идентификаторы в шаблоне должны поддерживаться твоими версиями клиентов и аккаунтами.
Полезные ссылки: [Codex CLI](https://developers.openai.com/codex/cli/),
[Claude Code](https://code.claude.com/docs/en/overview),
[OpenCode](https://opencode.ai/docs/).

## Первая задача

Подготовь отдельный Git-репозиторий для пилота. Сохрани исходную версию коммитом,
чтобы было удобно проверить результат. Пример ниже выполняет обзор README и настроек
Python-проекта; его можно запустить на самом репозитории Veacode.

```powershell
uv run veacode submit --spec examples/task.toml --workspace .
uv run veacode list
uv run veacode resume TASK_ID
```

Подставь полученный `id` вместо `TASK_ID`. `submit` только сохраняет задачу;
`resume` начинает или продолжает выполнение. Одной командой:

```powershell
uv run veacode run --spec examples/task.toml --workspace .
```

Для своего проекта укажи его путь через `--workspace`, а постановку сохрани в TOML:

```toml
goal = "Исправь конкретную ошибку и добавь необходимую проверку её поведения."
kind = "implementation"
read_only = false
constraints = ["Сохрани публичный интерфейс", "Изменяй только файлы по задаче"]
checks = [["{python}", "-m", "unittest", "discover", "-s", "tests", "-v"]]
```

Уточни `goal` и выбери команды проверки именно для этого проекта.
`checks` — доверенные локальные команды, которые выполняются от твоего имени.
Они задаются до запуска, массивами аргументов; `{python}` означает интерпретатор Veacode.
Используй только проверки, которые безопасно повторять: контроллер может запустить их
заново после остановки. Деплой, миграции и внешние отправки в `checks` не входят.
Для задачи с изменениями нужна хотя бы одна проверка.
Доступные `kind`: `implementation`, `simple`, `debugging`, `research`.

## DeepSeek через OpenCode

В первой версии DeepSeek — единственный платный API. Он выключен по умолчанию:

```toml
[policy]
allow_deepseek = false
```

Когда разрешишь платную работу, установи `allow_deepseek = true` и передай
`DEEPSEEK_API_KEY` в окружение процесса через свой локальный способ хранения секретов.
Значение ключа не добавляй в TOML или Git. Это разрешение действует для следующих
запусков с этой конфигурацией: повторных вопросов и денежных потолков контроллер не вводит.
Ограничения времени и числа исправлений защищают от зависаний и бесконечных циклов.

Маршрут `deepseek` запускает OpenCode с прямым DeepSeek API. Профили OpenCode с
`opencode.json`, `opencode.jsonc` или `.opencode` в рабочем проекте пока не поддержаны
этим адаптером. [Настройка провайдера DeepSeek](https://opencode.ai/docs/providers/#deepseek).

## Продолжение после остановки

```powershell
uv run veacode status TASK_ID
uv run veacode events TASK_ID
uv run veacode resume TASK_ID
```

Контроллер сохраняет план, результаты попыток, проверки и краткие отчёты.
При распознанной недоступности маршрута он пробует следующий разрешённый маршрут.
Если все закончились, задача остаётся сохранённой и её можно продолжить позже.

Статус `needs_reconciliation` означает, что исход действия неизвестен или файлы
изменились после контрольной точки. Проверь события, текущие изменения Git и состояние
предыдущего процесса. Когда разберёшься с результатом, выполни:

```powershell
uv run veacode resume TASK_ID --reconcile
```

Этот флаг принимает текущее состояние для нового планирования и проверки.
Он не завершает чужой процесс и не разрешает повторять непроверенное действие.
Пока предыдущий исполнитель жив, контроллер продолжение не запускает.

По умолчанию состояние находится в `.veacode` текущего каталога. Запускай команды
из одного каталога или указывай одинаковый абсолютный `--state-dir`.
Если состояние хранится внутри рабочего Git-репозитория, каталог должен находиться
под `.veacode`; другое расположение внутри репозитория отклоняется. Каталог вне
рабочего репозитория тоже поддерживается.
Для собственного файла маршрутов у `doctor`, `routes`, `run` и `resume` есть `--config`.

## Границы первой версии

Работа проходит последовательно: план → реализация → локальные проверки → ревью.
Коммиты, объединение веток, деплой и миграции остаются за пользователем.
Контроллер продолжает только задачи, которые сам сохранил. Он не переносит произвольную
уже открытую интерактивную сессию Claude Code между моделями.

Skill [skills/veacode/SKILL.md](skills/veacode/SKILL.md) можно подключить в ведущем агенте,
чтобы тот создавал управляемые задачи. Он поставляется в репозитории и не устанавливается
автоматически. Уже работающий skill Claude → Codex остаётся отдельным и сохранённым.
Одного skill недостаточно для восстановления сессии, запущенной вне контроллера.

Бесплатные модели, OpenRouter, другие платные API, денежные лимиты и параллельная работа
отложены. Текущая реализация ориентирована на локальный CLI; проверка на других ОС
и совместимость конкретных версий CLI отражаются в [docs/STATE.md](docs/STATE.md).
Подробные контракты и ограничения — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Разработка

Для демонстрации без моделей и ключей:

```powershell
uv run python examples/offline_demo.py
```

Она создаёт отдельный тестовый репозиторий, имитирует недоступность основного маршрута,
исправляет функцию сложения через локального исполнителя и запускает настоящие тесты.
Повторный запуск требует нового каталога: существующие файлы демонстрация не перезаписывает.

Для живого пилота из обычного терминала:

```powershell
uv run python examples/live_pilot.py --config veacode.toml --route codex
```

Пилот создаёт отдельный Git-проект. Основной маршрут намеренно недоступен, а выбранный
резерв действительно выполняет планирование, исправление и ревью. Контроллер проверяет
неизменность тестов и запускает три проверки сложения. Скрипт возвращает `completed`
только после прохождения проверок и приёмки. `--prepare-only` создаёт задание без вызовов моделей.

Для маршрута `deepseek` можно передать ключ через `DEEPSEEK_API_KEY` или только для пилота
через `--deepseek-key-file .veacode/deepseek.key`. В конфигурации при этом должно быть
разрешено `allow_deepseek = true`. Файлы `.veacode` исключены из Git.

```powershell
uv run python -m unittest discover -s tests -v
uv run ruff check .
uv --cache-dir .venv/uv-cache build
```

Тесты используют временные Git-репозитории, подставные CLI и обычные дочерние процессы.
Они не вызывают модели и не требуют ключей. CI запускает тесты на Windows и Ubuntu
с Python 3.12 и 3.13; фактический результат виден в GitHub Actions после публикации репозитория.
